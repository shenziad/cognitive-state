# exp001 试验协议 v0.1（待研究者审阅）

## 研究范围与单位

首轮考察**同一任务中断后的续做**。一个实例是截断点前历史 `H_t`、当前虚拟环境及可观察成功条件。截断点后统一发出“继续原任务”，不重新提供目标、约束或参考答案。提取阶段不提供未来新目标，不测试跨目标迁移。

数据集 `exp001-pilot-v0.1` 有 12 个合成配置修复任务。任务、历史和候选参考状态由助手离线制作；它们不是自然采集的长期 Agent 轨迹。首轮用于检查方法、提示与评分器，不用于宣称行为等价或普遍优于摘要。

## 条件

| 条件 | 执行器接收的内容 | 提取成本 |
| --- | --- | --- |
| `full_context` | 截断前历史的完整 JSON | 无 |
| `summary` | LLM 生成的普通文字摘要 | 记录实际 API 用量 |
| `cognitive_state` | LLM 提取、结构校验后的 G/W/F JSON | 记录实际 API 用量 |
| `reference_state` | 离线制作的候选 G/W/F JSON | 制作成本未测量，不能当作端到端成本优势 |

`reference_state` 全部 `review.status=pending`，不是人工 gold standard。审核状态及来源消息 ID 随运行保存，用于诊断表示结构与自动提取的问题。Summary 提示也允许保留目标、约束、证据、失败尝试和待办，采用有竞争力的摘要基线。

## 公平性与输入边界

- 所有条件共享执行模型、temperature、执行提示、工具、步数上限与环境初始状态。
- 每个实例每次重复都重建环境；以固定随机种子打乱条件顺序。此种子只控制运行顺序，不保证模型输出确定。
- 提取器只收到 `history` 与表示预算；不会收到 environment、rubric、reference 或后续工具结果。
- 环境通过 `read_file` 才向执行器公开当前运行手册。评价用的目标值保留在评分侧。
- Summary、自动 CS 和候选 CS 采用同一**表示大小上限**，不保证实际长度恰好相同。正式研究还需预算梯度或长度匹配分析。
- 超预算或无效 CS 不截断、不人工修复，也不转为 Full Context；保存错误并计为失败。
- Full Context 不受压缩预算限制。当前历史较短，不能据此评价超长 Context。

## 环境与工具

环境在内存中，操作 `config/service.json`、当前/旧版 runbook 和日志。四个工具：`read_file(path)`、`set_config(key,value)`、`run_check()`、`finish(status)`。一次模型输出只允许一个 JSON 动作。所有动作及观察保存，评分不要求唯一行动序列。

`run_check` 只返回通过与否，不直接暴露目标值；目标可从当前 runbook 推导。未知工具、错误路径或参数收到错误观察，正确恢复后仍可完成任务。保护字段即使改后恢复，也保留曾违反约束的记录。

## 固定评分规则

| 指标 | 本试验的具体规则 |
| --- | --- |
| Task Success Rate | 目标字段全部正确、保护字段未被违规修改、最后一次修改后检查通过，并以 `completed` 结束的实例比例 |
| Final Goal Completion | 最终目标字段与保护字段检查中通过的比例；不等同于完整任务成功 |
| Tool Usage Correctness | 合法且未违反保护字段约束的工具调用占全部调用的比例 |
| Decision Consistency | 四项检查的通过比例：修改前读取当前证据、遵守约束、不重复已知失败修改、经验证才宣称完成 |
| Token Reduction | 同实例同重复下，初次 Executor API 输入 Token 相对 Full Context 的降幅 |
| End-to-end Token Reduction | 提取与全部执行调用的输入/输出 Token 总量相对 Full Context 的降幅；候选参考状态不计算此降幅 |

“修改前读取证据”衡量本任务的决策依据，不是唯一允许的路线。猜中配置并验证成功可以得到 Task Success，但该决策检查项可能失败。纠正过的非法调用影响工具指标，不自动抹掉已完成的目标。Token Reduction 可为负，表示成本增加。

失败和提取错误保留在分母中。缺失 API 用量记为 `null`，不当作零。通信异常可能产生未报告成本，该次总成本设为 `null`。聚合报告每项指标实际可观察的运行数；小样本只做描述性比较。

## 预算与 Token 口径

默认 mock 预算为 2200 **UTF-8 bytes**，字节不称为 Token；mock 的 Token 指标为 `null`。

真实 API 示例使用 512 的本地 tokenizer 单位上限，需要研究者选择模型对应的 `tiktoken:<encoding>`。不同服务的 tokenizer 未必兼容，必须核对；结果记录所选计数器。表示预算由本地计数器检查，成本由服务报告的输入/输出 Token 记录，两者分开。生成输出上限单独配置为 2048，不用它冒充表示长度。

2026-10-02 接入 SiliconFlow DeepSeek-V4-Flash 的配置采用 2200 UTF-8 bytes 上限，因为没有经过核验的 DeepSeek 本地 tokenizer。生成使用 max_tokens=2048、enable_thinking=false；Token 成本来自服务返回的 usage。它属于相同字节上限的先导试验，不能表述为精确匹配 Token 预算的比较。

## 运行与数据留存

每次创建新输出目录，保存实际 config、运行 manifest、数据及提示副本、调用消息与响应、行动轨迹、实例 JSON、`results.json` 和 `summary.json`。manifest 包含 Git 提交、dirty 状态和代码/输入/提示 SHA-256。现有结果目录不覆盖，配置均无明文凭据。

默认运行 12 × 4 × 1 = 48 个 mock 组合。真实 API 示例只选两个实例、各三次重复，并有请求次数上限；它不是货币预算。真实费用上限、模型兼容性、采样与重复数需要接入时再确定。

## 解释与后续决策

1. Full Context 也频繁失败：先分析任务、评分器、执行提示或基础模型能力。
2. 候选状态经审核后有效、自动 CS 失败：定位提取遗漏、错误信念或无效 JSON。
3. 审核状态也失败：检查 G/W/F 是否缺少可行动信息，以及预算是否过小。
4. 三个核心条件都很好：说明这些任务不能区分方法，需要增加真实轨迹和更有区分力的任务；不能据此宣称 CS 优于 Summary。

正式验证 H1–H3 前另行确定真实任务集、独立测试集、样本量、统计分析与可接受性能损失。当前环境把答案写在 runbook 中，可能产生天花板效应，且尚不能证明 Frontier 的独立贡献。
