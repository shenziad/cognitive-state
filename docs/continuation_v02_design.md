# Continuation v0.2：状态信息、恢复成本与公平比较

## 本阶段要回答什么

在共同执行器完成独立接口校准后，比较 Full Context、竞争力较强的任务导向 Summary 与自动 Cognitive State。这里的问题是：**什么状态信息影响后续行动，以及丢失后能否恢复、需要付出多少成本？** 候选参考状态仅供来源审核，不加入主条件的胜负比较。

本版本共 14 个新实例：6 个反事实配对、2 个对照。没有复用上一轮失败实例，也没有依据真实模型分数修改本版本内容。构造和审核均为离线过程；实际模型结果应另外保存。

## 配对设计

| 配对 | h04 的变化 | 正确续做 | 无历史统一恢复策略 | credits：历史 / 恢复 |
|---|---|---|---|---|
| goal | 最新收件目标改为 retention / 仍为 review | 执行当前收件操作 | 重查 owner scope，再发送 | 2 / 3，均可成功 |
| belief | 旧 ion 猜测被确认 / 被 flux 证据推翻 | 使用已确认原因对应的 remedy | 重跑隔离诊断，再处理 | 2 / 3，均可成功 |
| assumption | rune 默认被 tile 握手推翻 / 被 rune 握手确认 | 按当前握手编码 | 重做 negotiation，再编码 | 2 / 3，均可成功 |
| completed | oak / elm 已验证完成 | 只校准另一个 rack | 付费重取 ledger，再执行剩余工作 | 2 / 4，超过预算 3 |
| inflight | pearl / jade 请求已接受，通知待消费 | 消费真实已接受请求的 notice | 付费重取 request identity，再消费 | 2 / 4，超过预算 3 |
| information | cargo R29 / venue P63 已验证，另一项未知 | 只读取缺失证书，再匹配登记 | 重读两个证书，再登记 | 3 / 5，超过预算 3 |

goal、belief 和 assumption 的最终答案在两侧反转。completed 与 inflight 需要的下一步操作反转；information 的正确下一项查询反转，其实际两个证书值保持一致，最终登记操作因此相同。不能将 information 当作最终答案变化的配对。

每对只有历史中的 h04 关键证据/目标更新不同。公共工具目录、费用、预算、初始请求、干扰历史和证据位置相同。操作名采用离散标识，并由公共工具描述解释其含义；操作排序不标识正确答案。环境初始状态或可观察结果在需要时随 h04 变化，以维持世界与历史的一致性。因此本设计是“公共接口相同的反事实”，不宣称所有配对的隐藏世界相同。

错误不可逆操作的任务规则在两侧对称。预条件探测、重复执行和账本恢复都有真实 credits 成本。免费 catalog 只返回工具描述和价格，不返回目标、世界状态、当前读数或评估 rubric。不可用 archive 查询也不返回旧证据。

## 无历史恢复对照

`task.recovery_context` 是字符串，包含 **原始 h01 请求、h02 公共工具定义，以及可重新取得哪些信息的说明**。它不包含 h04 更新、实际已完成身份、真实在途请求身份或已验证证书值。

这个对照与 Full Context 的差别包含后来目标更新本身；它是历史遗失后的恢复条件，不能解释为与 Summary 等量或等信息的公平压缩条件。每对两个成员的 recovery_context 完全相同。

`review_cases/*.json` 保存一个统一的、依据新观察自适应分支的恢复策略及离线实例化轨迹。它们是构造审核材料，不能送给模型。对于前三组，这些策略在两侧都成功，并比保留历史多花 1 credit；这有意保留“历史可以重获但有成本”的情形。

后三组的所示恢复策略超预算。这不等于穷尽所有无历史策略，模型仍可能偶然猜中，或者利用操作反馈选择行动。可接受路径交换和有成本的错误预条件探测已审计，但不能据此宣称理论上所有无历史策略必失败。尤其评估器不能区分“猜中历史已经读取的值”和“从表示记住该值”，需要结合具体轨迹解释。

## 两个对照

1. `control_recoverable`：所有路由证据都可在当前环境读取。历史和无历史均应通过读取当前证据完成任务。这用于检查是否把信息压缩或无历史输入变成工具调用障碍。
2. `control_completed`：隐藏世界中两个验证已完成，历史有签名收据；仅需 finish。无历史上下文只保留原任务，不能提供 all-done 截止点事实。由于最终世界状态已经满足目标，直接 finish 也可能成功；成功只能说明结束动作合适，不能证明输入包含完成证据。

## 长度和位置

六对分别放入 8、24、12、32、16、40 个其他工作区已关闭档案。关键 h04 位于早、中或末尾，每对一致。干扰记录内容不同，而不是重复同一段填充。干扰的旧目标、编码、校准、请求和证书都明确属于其他工作区。

长度与任务类型绑定，因此本轮**不能单独估计历史长度或证据位置的因果效应**。后续需要在同一任务上交叉长度与位置。如果出现性能差异，也不能直接称为长期记忆效应。

## 消融接口

每个 task 的 `ablation_progress_terms` 是大小写不敏感的词组列表，只指向真实进度 facts，如“calibration completed”或“pending reservation”。进度消融应只删除自动 CS 的 `world.facts` 中匹配这些词组的条目，并将名称明确写为“进度 facts 删除”。

相同进度可能仍出现在 Goal、Frontier 或其他未匹配事实中。因此这项消融并不是彻底删除所有进度信息；结果为零不能证明该信息无用。其它消融也应保存原表示与改动表示，报告残留与重建机会。

本版本没有“当前仍未确认、必须先验证”的活跃信念实例：belief 两侧都已有最终控制证据，assumption 两侧也都有当前握手。候选状态因此没有必要保留的 beliefs/assumptions。若运行“不确定性条目删除”，该消融对候选为 no-op，对自动 CS 至多删除模型仍保留的旧猜测。它不能有效检验活跃不确定性信息的必要性；应统计实际改动条目，并把这个覆盖缺口明确列入结果。需要下一版本新增适合该问题的任务，而不是根据本轮分数调整本版本。

这里的 credits 是合成环境的工作/恢复预算，与 API Token 或实际费用不同。报告应同时列出任务成功、恢复步骤、credits 和模型 Token；不能把 credits 的变化直接换算成 API 成本。

## 候选状态来源

所有 `references/*.json` 标为 `assistant_generated / pending`。每个候选的具体操作名和资源名均已在本实例 h02 的公共工具记录中出现；不会引用作者从隐藏 fixture 才知道的名字。最新世界/进度来自 h04，早先猜测和默认条件来自 h03。未查询证书的未来值不写入候选。

来源消息 ID 和构建检查只能提供可审核的线索，不能替代独立语义审核。候选可能更明确地表达下一步动作，所以它们保留为来源审核材料，而不是主比较条件。

## 离线审核与复现

```powershell
.\.venv\Scripts\python.exe scripts/build_continuation_v02.py --output <新的不存在目录>
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_continuation_v02.py -v
```

构建器拒绝覆盖已存在的输出目录。它在写入前检查 14 个正确轨迹、12 个反事实交换轨迹、统一恢复轨迹的成功与 credits、每对公共选择/预算一致、候选 JSON 合法且不超过 2200 UTF-8 bytes。冻结数据的 `construction_audit.json` 保存检查结果；任务、环境、候选和审核轨迹分别保存，模型输入仅取对应条件允许的部分。

这个集合仍是合成、单次中断、小规模任务。它适合定位表示、恢复和执行成本，不能代替自然任务及多次状态演化验证。
