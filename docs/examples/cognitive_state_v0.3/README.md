# v0.3 设计示例：接受后继续消费通知

状态：作者编写的规范示例，供研究者审阅；没有运行模型或模拟工具，不是新实验成绩、人审 gold 或最小长度证明。独立 state schema 版本为 v0.3，尚不兼容现有 v0.2 parser。

## 文件与可见边界

- [public_history.json](public_history.json)：初始提取器可见的 h01–h04；含用户要求、公共工具契约、真实阶段形式的设计观测及当前预算。
- [state_before.json](state_before.json)：仅依据 h01–h04 编写的状态；公开工具契约另作为所有条件相同的运行接口输入。
- [completion_event.json](completion_event.json)：假设后续实际执行成功时才到达的 h05；它不是初始提取输入。
- [state_after.json](state_after.json)：只在收到 h05 后成立的更新示例。

这里的 consume 成功契约明确说明 fulfilment，并返回完成证据。它是下一版公共接口的设计材料，不是对旧实验接口或旧结果的追溯修改。各表示条件都必须获得该契约；不能只向 CS 提供。

## 初始状态为什么可以直接行动

h03 提供已接受、仅一个请求、尚未 fulfilled、通知 pending；h02 说明 consume_Z 的前提、效果及价格；h04 提供当前 3 credits。故没有必要重新询问接受方。候选动作 consume_Z 花 2，符合已知预算；ledger 花 2 后再 consume 花 2 不可行。

初始状态没有偷看 h05，也没有把候选行动当成已执行。source_refs 供审计定位，必要事实已写入活动内容；执行器不需要也不允许免费调回 h03 原文。

## 事件对更新的要求

| 收到的公开事件 | 应如何处理 |
|---|---|
| 没有新事件 | 不新增接受方身份缺口；保持 accepted/pending |
| h05 明确消费成功且 fulfilled | 新增完成观测，操作阶段改为 completed，关闭 ob1，移除候选计划 |
| 收到明确 cancellation | 原 accepted 判断不再支持消费；重新评估目标、约束和工具允许的恢复；不能自动重发 |
| 工具调用超时，没有效果证据 | 操作阶段为未知或仅 issued；保留 handle，依据公共恢复接口处理；不能假定已经完成或完全未执行 |
| 当前额度改为 1 | 原候选动作不可执行；保留尚未完成义务，检查公开恢复/等待可能，不能编造低价动作 |
| 用户增加独立验证要求 | G 增加有来源要求，验证成为合法义务；不可简单以“已解决不重开”禁止必要验证 |

只有 h05 提供了完整后状态；表中其他分支是设计要求，没有额外编造观测结果。真实任务中并非每个工具都有 cancellation、恢复或幂等接口，不能凭该表假定它们存在。

## 需要审阅的取舍

前后状态仍有一定冗余，例如执行阶段和实际效果。这是为了清楚展示二者不等价，不声称每个字段都必须永久保留。后续用等价紧凑编码及语义消融检验冗余能否删除。

G 的来源定位、W 的操作阶段、F 的可选计划增加长度。是否值得这些开销，要用任务效果与全部更新/执行成本判断。此处没有套用 1400/2200 字节上限，也没有宣称新设计已经解决自动生成超限。
